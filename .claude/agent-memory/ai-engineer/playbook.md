## Оцінка собівартості AI-продукту до написання коду

**Коли застосовую:** засновник описав продукт із кількох AI-модулів і треба сказати,
чи витримає це економіку — **до** того, як команда щось напише.

**Кроки:**
1. **Скіл `claude-api` — першим.** ID моделей і ціни ніколи з памʼяті.
2. Зібрати прайс решти постачальників у `api-prices.md` (ремесло) з датами й мітками.
3. **Виписати припущення окремою таблицею перед розрахунками** — токенізація мови,
   довжина документа, довжина голосової нотатки, розмір системного промпту. Без цього
   числа виглядають точнішими, ніж є.
4. Собівартість **одного** запиту по кожному модулю: Free-сценарій і Pro-сценарій окремо.
5. **Помножити на частоту → доларів на користувача за місяць.** Це справжня одиниця.
6. Окремо позначити модулі, де **частоту задає система, а не людина** — там немає
   природної стелі.
7. Знайти модуль-домінанту (зазвичай один зʼїдає >50 %) і порахувати альтернативу йому.
8. Порахувати важелі: Batch API (−50 %), кешування (reads 0,1×), детермінований
   передфільтр перед моделлю.

**Де підтвердилось:** symplexy / Symplexy OS, 2026-08-04 — кроки 5–7 знайшли те, чого
не видно з ціни запиту: найдешевша операція (0,1 ¢) виявилась найдорожчим модулем місяця
($1,20), а один зовнішній API (Gamma) дав 92 % собівартості свого модуля.

**Коли НЕ застосовувати:** коли є реальна телеметрія. Виміряні частоти завжди б'ють
припущені; тоді цей плейбук — тільки для нових, ще не запущених модулів.

## Перевірка зовнішнього API на придатність — три питання, не одне

**Коли застосовую:** будь-який сторонній API потрапляє в архітектуру продукту.

**Кроки:**
1. **Чи є публічний API взагалі** — не плутати «є інтеграція з Zapier» з «є REST API».
2. **Технічні ліміти** — rate limits, квоти, стеля на користувача і на проєкт.
3. **Вартість** — за одиницю і за місяць очікуваного обсягу.
4. **Умови доступу** — і це найважливіше:
   - верифікація / аудит (скільки коштує, як часто, скільки триває);
   - **чи дозволяє ToS будувати поверх платний продукт і перепродавати генерації**;
   - чи не знято модель з API (перевіряти, а не вважати наявною).
5. Якщо пункт 4 не закритий — **не писати «блокерів немає»**. Писати «не перевірено» і
   передавати `legal-compliance`.

**Де підтвердилось:** symplexy, 2026-08-04 — Gmail: квоти з 400-кратним запасом, але
щорічний аудит $500–$4 500. Gamma: API є і працює, але ToS на перепродаж не перевірено,
і це лишилось найбільшим ризиком звіту.

**Коли НЕ застосовувати:** для внутрішніх сервісів своєї ж команди — там пункт 4 порожній.

## Робота в середовищі з жорстким лімітом зовнішніх запитів

**Коли застосовую:** WebFetch/curl заблоковані, WebSearch обмежений десятками запитів,
попередній прогін уже падав на ліміті.

**Кроки:**
1. **Створити файл результату ПЕРШОЮ дією**, зі скелетом розділів.
2. Ранжувати питання за тим, **що змінює висновок**, а не за порядком у ТЗ. Два-три
   блокери — першими.
3. **Дописувати кожен розділ у файл одразу**, не накопичувати в контексті.
4. Батчити незалежні пошуки по 2 в один хід.
5. Лишити резерв запитів; наприкінці **чесно написати, скільки витрачено і що не
   перевірено через ліміт**.

**Де підтвердилось:** symplexy, 2026-08-04 — 10 із ~20 запитів, обидва блокери із ТЗ
закриті, файл вижив би при падінні на будь-якому кроці.

**Коли НЕ застосовувати:** при вільному доступі до мережі — тоді пункт 3 зайвий оверхед.
