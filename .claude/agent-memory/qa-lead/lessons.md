
## 2026-08-01 — Регекс-сканер секретів у безпековому хуці не проходить власний boundary-test (case sensitivity)   [проєкт, де сталось: symplexy]
**Що сталось:** тестуючи `.claude/hooks/memory-guard.sh` (сканер секретів перед автокомітом
памʼяті), прогнав дослівно той самий regex поза git на зразках `Password="..."`,
`API_KEY=...`, `SECRET_TOKEN: "..."`. Жоден не спрацював — regex писаний без `-i`, тому
ловить лише малі літери (`password`, `api_key`, `token`), хоча найпоширеніша конвенція
для env-змінних — верхній регістр (`API_KEY`, `SECRET_TOKEN`). Патерн також вимагає
обов'язкові лапки навколо значення — unquoted стиль `.env`/YAML не ловиться взагалі.
**Чому:** автор хука писав regex «під приклад», не під клас атак. Класична помилка —
протестувати happy path (свій власний стиль написання секретів), не межові варіанти
регістру, лапок і формату (JWT, bearer-токени).
**Ціна:** непідтверджена (в цьому проєкті поки без інциденту через цю дірку), але
компанія вже мала реальний витік секрету через відсутність хука на іншій гілці — тобто
довіра до «хук би це впіймав» вже один раз була завищена.
**ПРАВИЛО:** будь-який сканер секретів/PII перевіряти обов'язковими boundary-тестами:
UPPERCASE та lowercase назва ключа, з лапками і без, з `=` і з `:`, і хоча б один
формат високоентропійного токена без явного ключового слова (JWT, bearer). Regex,
що «виглядає правильно», обовʼязково прогнати на цих 5+ варіантах ізольовано (поза
git, щоб не ризикувати реальним комітом) ДО того, як довіряти йому як бар'єру безпеки.
**Куди піднято:** MEMORY.md → топ-уроки: так

## 2026-08-01 — Дослівний вивід хука цінніший за переказ його логіки
**Що сталось:** статичне читання коду хука (`worker-memory-check.sh`) давало враження,
що поведінка правильна; лише прогін наживо (три послідовні виклики з тим самим
`session_id`, симулюючи «нічого не змінилось» і «щось змінилось») підтвердив це
фактично і водночас виявив, що перевірка не прив'язана до конкретного працівника —
лише до сесії загалом. Без живого прогону цей нюанс (важливий при 3-5 паралельних
працівниках, які компанія сама дозволяє) залишився б непоміченим.
**Чому:** читання коду перевіряє «чи логічно», а не «чи так насправді поводиться
разом з рештою системи (паралельність, спільні файли стану)».
**Ціна:** без цього прогону дефект Д2 (гонитва станів при паралельних воркерах) не
був би знайдений, лише вгаданий.
**ПРАВИЛО:** для хука/скрипта — завжди прогін наживо з реальним stdin/env, а не лише
читання коду; для дій, що небезпечно виконувати наживо (автокоміт+пуш) — ізольований
тест ідентичної логіки поза git, а не пропуск перевірки.
**Куди піднято:** MEMORY.md → топ-уроки: так
