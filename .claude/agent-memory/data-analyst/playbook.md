## Аудит наявності даних перед будь-яким розрахунком метрик
**Коли застосовую:** отримала запит «порахуй метрики X, Y, Z» у проєкті, де я ще не
працювала або де стан трекінгу невідомий. ДО того, як щось рахувати.
**Кроки:**
1. `company/projects/<проєкт>/founder-context.md` — секції «Гроші» і «Технічне».
2. Моя `projects/<проєкт>/state.md` — чи є збережені числа з датами.
3. `company/projects/<проєкт>/metrics-definitions.md` і `unit-economics.md` — чи існують.
4. `find` по `*.csv *.json *.sql *.db *.xlsx` — чи є вивантаження даних у репозиторії.
5. `Grep` по `MRR|CAC|LTV|churn|Stripe|GA4` — відсіяти шаблони від фактичних значень
   (шаблон описує, як записувати метрику; факт містить число з датою).
6. Результат аудиту записати в `state.md` рядком «що перевірено, щоб не шукати вдруге».
**Де підтвердилось:** symplexy 2026-08-01 — аудит зайняв ~5 хвилин і показав нуль
джерел даних; врятував від спокуси видати галузеві бенчмарки за метрики бізнесу.
**Коли НЕ застосовувати:** якщо в `state.md` уже є свіжий (< 1 міс) запис про стан
джерел — тоді достатньо перечитати його.

## Сортування запитаних метрик за відновлюваністю заднім числом
**Коли застосовую:** трекінгу немає або він неповний, а метрики просять уже зараз.
**Кроки:**
1. Розкласти кожну запитану метрику на доданки (CAC = витрати на залучення ÷ нові
   платні клієнти; LTV = ARPU × очікувана тривалість життя, тобто ARPU і churn).
2. Для кожного доданка спитати: **чи існує він десь поза нашою аналітикою?**
   Транзакції — так (платіжний провайдер). Рекламні витрати — так (кабінети реклами).
   Події продукту — ні, якщо їх не писали.
3. Метрики, всі доданки яких існують поза нашою аналітикою → «відновлювані», віддати
   негайно окремим треком.
4. Решта → назвати мінімальний час до появи. Для churn і LTV це щонайменше 2–3 місяці
   після старту трекінгу: раніше немає когорт, які встигли відвалитись.
**Де підтвердилось:** symplexy 2026-08-01 — з 4 запитаних метрик 1 (MRR) виявилась
відновлюваною з експорту платіжки, 3 — ні.
**Коли НЕ застосовувати:** коли трекінг уже працює і питання лише в якості даних.

## Розрахунок необхідного обсягу даних, коли даних немає
**Коли застосовую:** мушу сказати «даних немає», але рішення засновника все одно треба
чимось підперти.
**Кроки:**
1. Кількість конверсій під бажану точність: `k = (1.96 / відносна_похибка)²`.
   ±50% → ~15 · ±25% → ~61 · ±20% → ~96.
2. Перевід у трафік за сценаріями конверсії: `n = 1.96²·p(1−p) / (0.25·p)²`
   для напівширини 25% від самої `p`. Дати таблицею по кількох `p`, **явно позначивши
   їх як сценарії, а не як оцінку цього продукту**.
3. Перехресна перевірка: `n × p` має дати той самий порядок, що й `k` з кроку 1.
4. Висновок формулювати як межу рішення: «кілька сотень доларів дадуть одиниці
   конверсій — це похибка, більша за саме число».
**Де підтвердилось:** symplexy 2026-08-01 — дало засновнику масштаб рекламного
бюджету за відсутності будь-яких даних про продукт.
**Коли НЕ застосовувати:** якщо метрика не є часткою (наприклад, виручка) — там
потрібен розрахунок через дисперсію, а не через `p`.
