## ДЕФЕКТИ

### Д1 [ВИСОКИЙ] Сканер секретів у Stop-хуку не бачить секретів у верхньому/змішаному регістрі
Де: `.claude/hooks/memory-guard.sh` рядки 24-26. `grep -rInE` без `-i`. Патерн секретів
писаний малими літерами — `API_KEY=`, `Password="..."`, `SECRET_TOKEN:` не ловляться.
Патерн також вимагає лапки навколо значення — секрет без лапок (типовий `.env`/YAML
стиль) не ловиться навіть з `-i`. JWT/bearer токени не покриті жодним патерном.
Відтворено в ізольованій теці поза git з ідентичним regex: 0 збігів на
`Password="<довге-значення-32-символи>"`, `API_KEY=...`, unquoted password,
`SECRET_TOKEN: "..."`, JWT bearer — навіть з доданим `-i` спіймано лише 2 з 5.
Вплив: це останній рубіж перед автокомітом+пушем памʼяті. Компанія вже мала інцидент
(HF-токен, `company/ledger/lessons.md` 2026-07-30), де записано «хук заблокував би цей
коміт» — це твердження не повністю обґрунтоване для типового `HF_TOKEN=` чи
`HUGGINGFACE_API_KEY: "..."`.
Передано: security-engineer, devops-sre.

### Д2 [СЕРЕДНІЙ] SubagentStop-перевірка памʼяті не розрізняє паралельних працівників
Де: `.claude/hooks/worker-memory-check.sh`. Стан порівняння зберігається за
`session_id` (спільний для всіх підагентів однієї сесії), хеш — це загальний
`git status --porcelain .claude/agent-memory`, без прив'язки до конкретного
працівника/файлу. Компанія прямо дозволяє і заохочує 3-5 паралельних працівників
(`handoff.md`, «Паралельна робота»). Якщо один із паралельних оновив памʼять, а інший
ні, перевірка для недбалого може мовчки пройти, бо бачить лише «щось змінилось у
дереві з моменту останньої перевірки», без прив'язки до автора.
Логічно виведено з коду + документів компанії; не відтворено з реальними паралельними
підагентами (немає інструменту породити кілька одночасно з цього робочого місця).
Передано: devops-sre, principal-architect.

### Д3 [НИЗЬКИЙ] Хибна множина в SessionStart-хуку для 12-14 та X11+ працівників
Де: `.claude/hooks/session-brief.sh` рядок 16, case-конструкція для української
множини. Виняток «11 → працівників» прописаний лише для точного `N=11`. Відтворено
прогоном фрагмента коду для N=1..111: N=12,13,14 дають «працівники» (мало бути
«працівників»), N=111 дає «працівник» (мало бути «працівників»). При N=21 (поточний
стан) вивід коректний — дефект не проявляється сьогодні, спрацює при рості штату.
Передано: devops-sre, не терміново.

### Д4 [СЕРЕДНІЙ, потребує підтвердження] Контекст CLAUDE.md, вкладений мені на старті сесії, розходився з реальним HEAD
Вкладений на старті текст містив «20 постійних працівників» і шлях
`company/context/founder-context.md`. Реальний CLAUDE.md на диску (HEAD усіх трьох
гілок, `git diff HEAD` порожній) каже «21» і `company/projects/<проєкт>/founder-context.md`;
теки `company/context/` не існує взагалі. Не можу довести це системним патерном
(могло бути одноразовим для цієї сесії) — не моя зона діагностики механізму ін'єкції.
Передано: devops-sre, principal-architect.

### Д5 [ВИСОКА ВПЕВНЕНІСТЬ, не 100% доказ] MEMORY.md не був автоматично вкладений мені в системний промпт при старті
`memory-protocol.md` заявляє автовкладення перших 200 рядків MEMORY.md у системний
промпт при кожному запуску. На старті цієї сесії мій контекст містив дослівний
`.claude/agents/qa-lead.md`, але не містив вмісту MEMORY.md — перша дія сесії була
явний `Read` цього файлу. Вплив пом'якшений тим, що протокол і так вимагає ручного
читання MEMORY.md як кроку №1, тож дублювання рятує систему навіть якщо автовкладення
не працює. Не маю доступу до сирого системного промпту для формального доказу.
Передано: devops-sre, principal-architect.

### Д6 [ВИСОКИЙ, ПІДТВЕРДЖЕНО ДВІЧІ НЕЗАЛЕЖНО] Harness блокує субагентам `Write` файлів-артефактів workspace, яких вимагає власний протокол компанії
Де: інструмент `Write` цього середовища (не файл репозиторію) versus
`company/protocols/workspace.md` + `definition-of-done.md` §3, які прямо вимагають
результат-файл у `company/workspace/<задача>/*.md`.
Що саме: спроба `Write` у `company/workspace/2026-08-01-system-test/findings.md`
(файл, прямо названий у критерії «готово» цього тех-завдання) відхилена інструментом
з повідомленням «Subagents should return findings as text, not write report files.
Include this content in your final response instead.» — дослівно, побачено власними
очима в цій сесії.
Це ТЕ САМЕ блокування, що вже задокументувала `data-analyst` у `dead-ends.md` цієї ж
робочої теки раніше сьогодні (запис «2026-08-01 — data-analyst не зміг створити
файл-результат»), незалежно, на іншому файлі (`findings-data.md`). Я підтверджую
дефект другим незалежним відтворенням і уточнюю межу: `Edit` на вже існуючий
(нехай і порожній) файл із такою ж назвою — **проходить без блокування** (так я і
записав цей-таки `findings.md` — файл був заздалегідь створений оркестратором при
заведенні workspace-теки, тому `Edit` спрацював). Але для НОВОГО файлу, якого ще
не існує (випадок data-analyst), обхідного шляху через `Edit` немає — інструмент
вимагає наявний файл.
Вплив: критерій «готово» виду «запиши результат у company/workspace/.../X.md» є
**непередбачувано виконуваним** — залежить від випадкового факту, чи хтось заздалегідь
створив порожній файл-заглушку з такою назвою. Це підриває саму механіку робочих
тек, описану в `company/protocols/workspace.md` («findings.md — спільний блокнот
ланцюга... report.md — фінал») для будь-якого нового файлу, не лише вже наявних
`task.md`/`findings.md`/`dead-ends.md`.
Важливість: високий — це не гіпотетичний, а двічі-незалежно-відтворений збій самого
фундаментального механізму передачі знань між працівниками в ланцюгу (workspace
protocol), яким компанія явно пишається («Проблема 2 — втрата знань між
працівниками», `workspace.md`).
Передано: devops-sre / principal-architect — з'ясувати межі цього обмеження harness
і або (а) наперед створювати порожні заготовки всіх очікуваних workspace-файлів при
заведенні теки (обхід через попереднє існування файлу), або (б) прибрати вимогу
файлу-артефакту з тех-завдань і покласти створення workspace-файлів на оркестратора
з тексту працівника, як і рекомендувала data-analyst.
