# Протокол робочої теки задачі

Запозичено з архітектури Manus (рецитація цілей + файлова система як контекст) і
Kimi K2 (чергування «подумав → зробив → перевірив»). Розвʼязує дві реальні проблеми.

## Проблема 1 — дрейф цілі на довгій задачі

Модель тримає в увазі краще те, що **в кінці контексту**. На довгому запуску початкове
завдання «тоне в середині»: працівник поступово починає робити щось суміжне, а не те,
що просили. Manus виявив, що дешевий і сильний фікс — змусити агента **переписувати
свій чекліст** у міру роботи. Кожне переписування повертає ціль у кінець контексту.

## Проблема 2 — втрата знань між працівниками

Коли над одним результатом послідовно працюють четверо, вони спілкуються лише через мій
переказ. Те, що знайшов перший, доходить до четвертого спотвореним або не доходить.
Спільний файл усуває посередника.

## Структура

Одна задача = одна тека:

```
company/workspace/YYYY-MM-DD-<коротка-назва>/
  task.md         бриф + ЧЕКЛІСТ (переписується в ході роботи)
  findings.md     спільний блокнот ланцюга: факти з джерелами
  dead-ends.md    що НЕ спрацювало і чому
  report.md       фінал для засновника
```

Завершена задача → `company/workspace/_done/`.

Дрібна задача (один працівник, один крок) теки не потребує. Заводимо, коли:
працівників у ланцюгу двоє й більше, **або** робота триває довше кількох кроків,
**або** результат дорогий.

## task.md — рецитація

```markdown
# <Задача>
**Проєкт:** <назва>   **Ланцюг:** market-researcher → conversion-copywriter → …

## Результат
<одне речення: що має бути на виході>

## Чекліст
- [x] зібрано цитати клієнтів — 14 шт, findings.md
- [ ] ← ЗАРАЗ: текст головної сторінки
- [ ] макет
- [ ] трекінг форми

## Межі
- не чіпати схему БД
- не витрачати гроші
```

**Правило рецитації:** працівник **переписує цей чекліст після кожного значущого кроку**,
позначаючи зроблене і чітко вказуючи «← ЗАРАЗ». Не в кінці — по ходу.

Це не звітність для засновника. Це механізм утримання уваги на цілі.

## findings.md — спільний блокнот

Те, що наступний працівник у ланцюгу мусить знати. Факт без джерела не пишеться.

```markdown
## <дата> · <slug працівника>
- <факт> — джерело: <посилання / файл / запит>
- <факт> — **припущення**, не перевірено
```

Наприкінці роботи цінне звідси переїжджає в памʼять: ремесло → `lessons.md`/`playbook.md`,
факти бізнесу → `projects/<проєкт>/state.md`. Робоча тека — тимчасова, памʼять — постійна.

## dead-ends.md — помилки лишаються видимими

**Найважливіший і найменш очевидний файл.**

Природний порив — прибрати невдалу спробу, щоб «не смітити». Manus показав, що це
помилка: коли модель бачить у контексті провалену дію та її наслідок, вона **сама
зміщується від повторення** цього шляху. Прибрана помилка = помилка, яку наступний
працівник повторить.

```markdown
## <дата> · <slug>
**Пробував:** <що>
**Результат:** <що саме пішло не так, дослівно — вивід, помилка, відмова>
**Не робити:** <висновок>
```

Правило: **невдала спроба не видаляється ні з файлу, ні зі звіту.** Провал, зроблений
видимим, — це дані. Провал, прибраний із очей, — це майбутнє повторення.

## Самоперевірка перед звітом

Перед тим як віддати роботу, працівник проходить чекліст **по одному пункту** і на
кожному каже: виконано / не виконано / виконано частково — **з доказом**, а не з памʼяті
про власні наміри.

Це окремий крок, а не настрій. Різниця між «я зробив» і «я перевірив, що зроблено» —
це те, що відрізняє професіонала.

## Чого не робити

- Не заводити теку на дрібницю — це бюрократія без користі.
- Не тримати в робочій теці те, що має жити в памʼяті. Тека тимчасова.
- Не переписувати `dead-ends.md`, «щоб виглядало краще».
- Не залишати завершені теки в корені — переносити в `_done/`.
- Не дублювати `findings.md` у звіті цілком — у звіт іде висновок.
