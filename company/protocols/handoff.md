# Протокол передачі роботи

Працівники не спілкуються між собою напряму. Усе йде через оркестратора. Тому передача
мусить бути письмовою і самодостатньою.

## Форма передачі

Працівник, який передає, пише в кінці свого звіту:

```
## Передав далі
**Кому:** <slug працівника>
**Що потрібно:** <конкретний результат, не «глянь це»>
**Чому саме він:** <яка експертиза потрібна>
**Що я вже зʼясував:** <факти, щоб він не дублював роботу>
**Артефакти для нього:** <шляхи до файлів>
**Чого я НЕ перевіряв:** <його зона, я в неї не заходив>
**Блокує мене:** так / ні
```

Оркестратор перетворює це на тех-завдання за `task-brief.md` і запускає наступного.

## Правило невторгнення

Працівник **не робить роботу іншого працівника наполовину**. Це створює найгірший
результат: виглядає готовим, а зроблено непрофесійно, і ніхто не перевірить.

| Побачив | Не роби сам | Передай |
|---|---|---|
| уразливість у коді | не «підправляй трохи безпеку» | `security-engineer` |
| потрібні цифри | не оцінюй на око | `data-analyst` |
| потрібна цитата клієнта | не вигадуй | `market-researcher` |
| потрібен новий колір/шрифт | не вводь | `brand-designer` |
| потрібна юридична формула | не пиши з голови | `legal-compliance` |
| потрібно змінити архітектуру | не змінюй самовільно | `principal-architect` |
| витрата грошей | не рекомендуй без розрахунку | `finance-controller` |
| обіцянка про фічу | не обіцяй | `product-strategist` |

Виняток — дрібниця в межах твоєї роботи, яку неможливо відділити. Тоді робиш і **явно
позначаєш**: «зробив мінімально, потребує перевірки від `<slug>`».

## Типові ланцюги

```
Фіча:        product-strategist → principal-architect → fullstack-engineer → qa-lead → devops-sre
Лендінг:     market-researcher → conversion-copywriter → brand-designer → fullstack-engineer → data-analyst (трекінг)
Запуск:      product-strategist → security-engineer + legal-compliance (вето) → growth-lead → content-strategist
AI-функція:  product-strategist → ai-engineer → security-engineer → finance-controller (токени) → qa-lead
Реклама:     finance-controller (дозволений CAC) → market-researcher (мова) → paid-ads-buyer → data-analyst
Відтік:      data-analyst → customer-success → product-strategist
Ціна:        data-analyst + market-researcher → finance-controller → product-strategist → conversion-copywriter
```

## Зворотна передача (повернення роботи)

Працівник має право **повернути завдання**, якщо:

- не вистачає вхідних даних, і без них результат буде вигадкою;
- завдання не в його зоні;
- виконання порушує його червоні лінії;
- завдання суперечить уже прийнятому рішенню в `decisions.md`.

Форма:

```
## Повертаю завдання
**Причина:** <одна з чотирьох вище>
**Що потрібно, щоб я міг працювати:** <конкретний список>
**Хто це може дати:** <slug або «засновник»>
**Що я все ж зробив:** <частина, яку можна було зробити зараз>
```

Повернення — нормальна робоча ситуація, а не збій. Гірший варіант — виконати завдання
на вигаданих даних.

## Паралельна робота

Двоє можуть працювати одночасно, якщо:

- вони не пишуть в одні й ті самі файли;
- один не чекає результату іншого;
- їхні зони не перетинаються.

Інакше — послідовно. Двоє в одному файлі одночасно = втрачена робота.
